# A-3. 고려대 → KETI : 워크로드 메타데이터 규약

- **방향**: 고려대(스케줄러) → KETI(자원 분할)
- **목적**: 워크로드의 **역할**(보호 대상인가, 자원을 줄여도 되는가)을 파드에 실어 전달.
- **상태**: KETI 제안. **선택 사항이며 고려대에 요구하지 않는다** — 안 주셔도 동작한다(§미지정).
  annotation 키·매핑은 협의 대상.

## 왜 선언을 두는가 — ★근거가 바뀌었다 (Exp_131)

**이전 근거는 "관측으로 판정할 수 없다" 였고, 그것은 더 이상 맞지 않는다.**
MPS 하 DCGM이 device-level이라 프로세스 귀속이 안 되는 것은 그대로지만(Exp_75),
Exp_131에서 CUPTI를 워크로드 컨테이너에 주입하면서 **커널 단위 관측이 열렸고 분류가 실제로 된다.**

| 워크로드 | 관측 판정 (Exp_131 실측) |
|---|---|
| bert-large b8 | `COMPUTE_BOUND` / 신뢰도 HIGH |
| prefill | `COMPUTE_BOUND` / HIGH |
| decode b8 | `MIXED` / HIGH |

그럼에도 선언 항목을 남기는 이유는 둘이다.

**(1) 관측은 실행 뒤에야 답한다.** 분류가 정답에 닿는 데 약 1초가 걸린다.
더 나쁜 것은 그 전 구간이다 — 0.2~0.5초에서 **정반대 답을 HIGH 신뢰도로** 낸다
(커널 12개만 보고 `MEMORY_BOUND`라 답했고 최종 답은 `COMPUTE_BOUND`였다).
배치는 실행 전에 정해지므로 그 시점에 쓸 수 있는 것은 선언뿐이다.

**(2) 관측은 성질을 말하지 역할을 말하지 못한다.** `workload-class`는 자원 종류가 아니라
**역할** 선언이다(아래 필드 규약). 같은 모델이 배치 학습이면 자원을 줄여도 되는 쪽이고
저지연 서빙이면 지켜줘야 하는 쪽인데, **커널 트레이스는 둘이 똑같다.**
"이 작업의 응답 시간을 지켜줘야 하는가"는 SLO 판단이고 고려대만 안다.

## 전달 경로: 파드 annotation

```yaml
metadata:
  annotations:
    kraken.keti.re.kr/workload-class: "compute"    # 선택: compute | memory
    kraken.keti.re.kr/priority: "low"              # 선택: high | med | low (기본 med)
    kraken.keti.re.kr/pipeline-stage: "prefill"    # 선택: prefill | decode (LLM 단계)
```

### 필드 규약

- `workload-class`:
  - `compute` = 응답 시간이 중요하지 않은 작업 = **자원을 줄여도 되는 쪽**(예: 학습, 일괄 추론).
  - `memory` = 응답 시간을 지켜줘야 하는 작업 = **자원을 지켜줄 쪽**(예: 저지연 서빙).
  - ★ **역할 선언이지 자원 종류 선언이 아니다.** 응답 시간이 중요한 서비스가 실제로는 연산을
    많이 쓰더라도 `memory`로 선언한다 — 이름이 자원 종류처럼 보이지만 뜻은 "지켜줄 대상"이다.
- `pipeline-stage`와 `workload-class` **중복 시 매핑 규칙**: stage가 있으면 우선 적용 —
  `prefill`→`compute`(첫 응답, 배치성), `decode`→`memory`(토큰 스트리밍, 지연 민감). class를 명시하면 그것이 최종.
- `priority`: 동일 class 다수일 때 제어 몫 배분 힌트(현 feeder는 LSU 비례, priority는 향후 가중).

## annotation → env 변환: **KETI가 담당** (누가 하는지 확정)

현행 KETI 제어 계층은 파드 env `KRAKEN_WORKLOAD_CLASS`를 읽어 libbless가 `/class` 파일로 떨군다.
annotation을 env로 바꾸는 주체는 **KETI**다:

- **프로덕션**: KETI가 mutating admission webhook을 운영 —
  `kraken.keti.re.kr/workload-class` annotation → 컨테이너 env `KRAKEN_WORKLOAD_CLASS` 주입.
  고려대는 **annotation만** 달면 된다(env를 몰라도 됨).
- **본 데모 스텁**: webhook 대신 고려대 스텁이 annotation과 env를 함께 세팅(변환을 스텁이 대행).
  README에 "프로덕션은 KETI webhook이 변환"으로 명시.

## ★ 미지정 시 동작 — **안 주셔도 된다**

`workload-class` annotation이 **없으면** 아래처럼 동작한다. 선언은 요구가 아니라
**"자원을 줄여도 되는 작업"을 알려주는 선택 사항**이다.

| 선언 | 동작 | 결과 |
|---|---|---|
| **있음** | 선언대로 — 지켜줄 쪽은 풀고, 줄여도 되는 쪽은 줄인다 | 응답 시간이 보호되고 몫도 지켜진다 |
| **없음 (현재)** | 양쪽에 같은 방식을 적용한다 | 몫은 지켜지나 응답 시간 tail이 나빠진다 |
| **없음 (계획)** | 관측 판정으로 **자원을 더 주는 쪽으로만** 쓴다 | 판정이 틀려도 응답 시간 목표는 안 깨진다 |

### 계획 항목의 근거 — 오탐 비용이 한쪽으로 치우쳐 있다

관측(Deep Scanner)이 틀렸을 때,

- **더 줘서 틀리면**: 전체 처리량이 조금 낮아진다.
- **덜 줘서 틀리면**: 그 작업의 응답 시간 목표가 깨진다.

그래서 관측 판정은 **자원을 더 주는 방향으로만** 쓴다. 관측이 "연산을 많이 쓴다"고 해도
자원을 줄이지 않는다 — 그 작업이 지켜줘야 할 서비스일 수 있고, 그건 관측이 모른다.
**자원을 줄이는 것까지 허용하려면 선언이 있어야 한다.**

⚠️ **계획 항목은 아직 구현되지 않았다.** 현재는 선언이 없으면 양쪽에 같은 방식을 적용한다.
붙이기 전에 정해야 할 것 둘 —
관측 라벨은 `COMPUTE_BOUND`/`MEMORY_BOUND`/`MIXED` 셋인데 선언은 둘이라 **`MIXED`를 어디로
보낼지** 정해지지 않았고(실측에서 decode가 `MIXED`로 나왔다), **첫 1초 구간**은 여전히 비어 있다.

## 확인 필요 (고려대 협의)

1. **작업을 어떤 형태로 넘기는가** — 이것이 먼저다. 스케줄러가 제출 시점에 작업 성격을
   이미 알고 있으면 선언을 받는 편이 낫고, 모르면 안 받는 편이 낫다.
   **답이 나오기 전까지 KETI는 선언 없이 들어온다고 보고 만든다.**
2. `pipeline-stage` ↔ `workload-class` 매핑을 고려대가 확정할 것인가, KETI 기본값을 쓸 것인가.
3. 지연 SLO 수치를 annotation에 실을 것인가. 현 규격은 역할·우선순위까지만이고
   **SLO 수치는 고려대 알고리즘 몫이라 뺐다.**
4. 선언과 관측이 어긋날 때 — KETI가 그 사실을 알려주기만 할 것인가, 관측을 따를 것인가.
   (현 방침: **선언이 이긴다.** 어긋남은 드러내기만 한다.)
